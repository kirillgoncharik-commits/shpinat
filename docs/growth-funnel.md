## Страницы и CTA

- `/`: основной CTA «Подать заявку», «Посмотреть программу», «Задать вопрос»; существующий Calendly для знакомства сохранён в конце.

- `/apply/`: краткое описание и критерии участия, команда, анкета приблизительно на две минуты. Обязательны контакты, ситуация, стадия, задача, результат, готовность, источник и согласие; «что пробовал» необязательно.
- `/contact/`: отдельная короткая форма. Имя необязательно, требуется email **или** другой контакт, тема, сообщение, согласие.
- `/privacy/`: данные форм, источник, антиспам, сервисы доставки и аналитика.
- Все страницы: заявки, программа, вопрос, email и Calendly в footer. Шапка сохраняет мобильное меню и видимый CTA заявки.
- Обе формы показывают success state с номером обращения только после ответа сервера об отправке email. Calendly после отправки необязателен.

## Доставка и журнал

`POST /api/lead` → Pages Function → закрытый service binding `LEADS` → Worker `shpinat-leads`. У Worker нет публичного workers.dev, preview URL или внешнего маршрута. Он проверяет origin, размер запроса, поля, согласие, honeypot, Turnstile (success, hostname, action), дневной лимит 15 обращений с одного временного хеша IP.

Обращение сначала сохраняется в D1 `shpinat-leads`, затем отправляется через `MAILER` (Cloudflare send_email) на подтверждённый Gmail. Отправитель `call@shpinat.club`. Если посетитель указал email, Reply-To — его email; если только Telegram/WhatsApp, Reply-To не выдумывается, другой контакт указан в письме. Уведомление содержит ответы, UTC timestamp, номер, страницу, CTA, первую страницу, referrer и UTM. Необходима фактическая проверка Gmail: принятие сообщения почтовым сервисом само по себе не подтверждает получение.

D1 хранит имя, email, контакт, дату, тип, тему, source, landing, страницу, CTA, все ответы, версию согласия, status (`new`), outcome и статус доставки. Публичного API чтения нет. Работа с журналом — через Cloudflare D1 Console с доступом владельца. Поля status/outcome можно обновлять в Console. При ошибке доставки сервер возвращает ошибку, сохраняет `notification_status=failed` и разрешает повтор с тем же request_id. Уже отправленное обращение с тем же ID не посылается повторно.

Интеграция с отдельным Kirill OS не нужна для сохранности лидов: простой журнал уже реализован. Отдельный follow-up: при необходимости добавить в Kirill OS защищённый просмотр/обновление status/outcome из этого журнала; не делать его публичным.

## Аналитика

Используется существующий GA4, новый проект не создаётся. Google tag загружается только после согласия, события до согласия и после отказа не отправляются и не воспроизводятся задним числом. Формы и attribution работают независимо от согласия на GA4.

| Событие | Условие |
| --- | --- |
| `primary_cta_click` | Нажатие основного CTA заявки |
| `application_start` | Первое взаимодействие с полями заявки |
| `application_submit` | Сервер подтвердил сохранение и отправку email заявки |
| `contact_form_start` | Первое взаимодействие с полями вопроса |
| `contact_form_submit` | Сервер подтвердил сохранение и отправку email вопроса |
| `email_click` | Нажатие mailto |
| `calendly_click` | Нажатие реальной ссылки Calendly |
| `booking_click` | Сохранённое прежнее событие для сопоставимости baseline |

`booking_completed` отсутствует: внешний переход не подтверждает бронирование; для него понадобится проверенный Calendly webhook с достоверной записью.

Поля каждого события: `page`, `cta_location`, `referrer`, `landing_page`, `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `offer=shpinat`. Для анализа в стандартных отчётах GA4 можно зарегистрировать эти event-scoped custom dimensions; сырые параметры доступны в DebugView. Имена, контакты, ответы и ID обращений в GA4 не передаются. Конфигурация page_view заменяет полный URL очищенным URL, исключая посторонние query-параметры.

## Attribution

Первое касание сохраняется в `sessionStorage` под `shpinat.attribution.v1` до закрытия вкладки. При переходе главная → программа → заявка исходные UTM не перезаписываются. Referrer сокращается до origin. URL содержит путь и только четыре разрешённых UTM. UTM ограничены 120 символами и безопасным набором символов. Неподдерживаемые query-параметры, включая email и token, исключаются. UTM не должны содержать персональные данные. Расположение входного CTA хранится отдельно под `shpinat.cta.v1` и передаётся с формой.

## Privacy и эксплуатация

Согласие формы отдельно от аналитики, версия `2026-11-01`. Не передавать PII в GA4/UTM или логи. IP в lead log не сохраняется; хеш лимита меняется ежедневно и устаревшие записи удаляются. Запросы на доступ/удаление принимает публичный email. Владелец удаляет соответствующие строки D1 и письма при выполнении запроса. Регулярно пересматривать необходимость хранения старых лидов.

Production Turnstile допускает `shpinat.club` и его поддомены, сервер разрешает только `shpinat.club` и `www.shpinat.club`. Preview не может отправлять реальные обращения. Test keys не используются на production. CSP разрешает только официальный скрипт/iframe Turnstile и существующий Google tag.

## Публикация и проверки

Сайт остаётся в существующем Pages-проекте. Не загружать `public/` через Dashboard: он не компилирует Pages Functions. Использовать Wrangler `pages deploy public --project-name shpinat-pilot --branch main --commit-hash <SHA>` из чистого checkout опубликованного commit. Перед этим применить D1 migration и опубликовать закрытый Worker. Его секреты сохраняются при обновлении кода. `MAILER` должен быть ограничен реальным подтверждённым получателем; не публиковать его адрес в клиентском коде.

Локально: `npm test`, `npm run check`. Backend tests используют настоящий SQLite с schema migration и проверяют поля, согласие, origin, защиту, сохранение источника, доставку, повтор, сбой доставки и лимиты. HTML validator проверяет локальные ссылки/якоря, изображения и sitemap. Финальное доказательство — отдельный production readback и реальные письма обеих форм.
